# Эксперимент: внешний пик GPU <1000 MiB

Статус: подготовлен код, GPU-результата пока нет. Проверенная версия остаётся
`3088ce8cca7b54ddaa101afbf3196b02d9b9ff0a` с пиком 2063 MiB и временем
74.01 с; все 10 проверок в ней прошли. Текущий эксперимент находится в
личной ветке `memory1000`. Автоматические Kaggle-запуски для него не создавались.

## Что ограничивает память

Для Qwen2.5-1.5B в этой задаче точные размеры основных весов дают:

| Объект | Размер, MiB | Где хранился в проверенной версии |
|---|---:|---|
| Tied embedding/head, FP32 | 890.25 | CPU после PEFT setup |
| Полный Half-операнд head | 445.125 | GPU во время head forward/backward |
| Packed NF4-байты всех матриц decoder | 624.75 | GPU |
| Из них MLP gate/up/down | 551.25 | GPU |
| Остальные attention-матрицы | 73.50 | GPU |
| Бюджет удерживаемых saved-активаций | до 256 | GPU |

Это размеры тензоров, а не независимые слагаемые измеренного пика. Дополнительно
нужны scale metadata, LoRA, градиенты, optimizer state, временные матрицы,
CUDA context и память, удерживаемая штатным аллокатором. `nvidia-smi` считает
весь процесс, а не только `torch.cuda.max_memory_allocated()`.

Даже только 624.75 MiB NF4 + 445.125 MiB head превышают 1000 MiB. Уменьшить
один бюджет активаций недостаточно. Кроме того, перенос embedding на CPU
после загрузки не исключает его первоначального CUDA-пика, а обычный
`model.to(cuda)` способен временно вернуть весь FP32-вес на GPU.

## Реализованный кандидат

1. Собственная обёртка загрузчика Qwen2 создаёт локальную копию конфигурации
   загрузки: embedding и tied head материализуются сразу на CPU. Остальные
   веса по-прежнему загружаются и квантизуются штатным NF4-квантизатором на
   CUDA. Его алгоритм, double quantization и dtype не меняются. Исходный
   загрузчик и его allocator warmup выполняются; warmup получает фактическое
   размещение тензоров. Настройки аллокатора и замеров не изменяются.
2. Собственный `_apply` для frozen CPU-весов сохраняет их CPU-хранение при
   последующих framework `model.to()`. Запрошенный dtype применяется, а
   устройство исполнения embedding сохраняется отдельно. Реальные значения
   параметров и tie embedding/head остаются прежними.
3. Frozen MLP NF4-байты переносятся на CPU после стандартной подготовки PEFT.
   Gate/up объединены в один CPU packed buffer; оригинальные параметры
   используют представления тех же байтов. Готовые scales вычислены штатно
   на CUDA и скопированы lossless. На GPU одновременно загружаются операнды
   текущего MLP; backward получает их снова с CPU и сохраняет прежний
   recomputation. NF4-параметры не деквантизуются на CPU и не квантизуются заново.
4. Head обрабатывает словарь блоками 8192: для width 1536 вес одного блока
   занимает 24 MiB вместо полного 445.125 MiB операнда. Все классы словаря,
   CE, entropy, argmax и rewind остаются вычисляемыми. Этот streamed head
   ранее прошёл отдельные GPU-тесты, но не полный успешный training run.
5. Бюджет удержания saved-активаций уменьшен с 256 до 64 MiB. Остальные
   большие активации сохраняются в pinned CPU memory без изменения значений.

Все переносы выполняются внутри измеряемого процесса на исходном CUDA stream.
Встроенные Soup offload/checkpointing/packing режимы не включены. Модель,
данные, батчи, LoRA и optimizer settings прежние. Код `harness/`, `tests/`,
`task/`, `templates/` не изменён. Чужие готовые kernel-библиотеки не добавлены.

## Насколько достижима цель

По размерам рабочих тензоров схема допускает пик ниже 1000 MiB. Самое
неопределённое место — загрузка и CUDA runtime: во время исходной загрузки
decoder ещё содержит до 624.75 MiB NF4-байтов плюс metadata и временную
квантизацию. Их внешний пик требуется измерить. Число 1000 не используется
в коде для сокрытия или изменения измерений; заранее обещать прохождение нельзя.

Цена — CPU RAM и PCIe-трафик. Одна передача всех MLP весов равна примерно
551 MiB; forward и backward вместе требуют около 1.1 GiB на шаг. Streamed
head читает примерно 890 MiB весов на шаг суммарно в forward/backward,
плюс пересылки активаций. Возможное замедление может нарушить допуск
времени ≤110% базы, даже если память будет ниже цели.

В streamed head меняется порядок редукции backward по словарю; совпадение
полного обучения побитово не обещается. MLP storage проверяется на точное
совпадение выходов и масштабированных градиентов; полный loss/eval обязан
пройти штатные допуски. Низкая память при провале хотя бы одной проверки
не считается допущенным результатом.

## Проверка

Добавлены GPU-тесты на CPU storage и повторный `model.to(cuda)`, точные MLP
outputs/gradients, сохранение исходных NF4-байтов и отсутствие GPU NF4-весов
в saved tensors. Интеграционный тест генерирует маленький локальный checkpoint,
проходит настоящий HF loading → CUDA NF4 → PEFT → LoRA → forward/backward,
сравнивая loss и trainable gradients с обычным размещением. Hub-загрузки
для этого теста не нужны. Локально GPU и PyTorch отсутствуют: эти тесты
написаны, но их успешное прохождение пока не подтверждено.

В Kaggle использовать свежую сессию T4 и точный COMMIT. Выполнить обычные
solution-тесты и исходный harness/check_rules/score. Для одного эксперимента
достаточно одной сессии с предусмотренными шаблоном повторами. ZIP собирает
`automation/archive_results.py`; он включает result/checks, метрики, логи,
конфиги, профиль и метаданные текущего checkout. Адаптеры и кэши не включаются.

API-основания:
[PyTorch saved tensors hooks](https://docs.pytorch.org/docs/2.11/autograd.html#torch.autograd.graph.saved_tensors_hooks),
[PyTorch pinned memory](https://docs.pytorch.org/docs/2.11/notes/cuda.html#use-pinned-memory-buffers).
Интеграция изучена по исходникам transformers 5.16.1 и bitsandbytes 0.50.2,
используемым в ранее проверенном окружении; их loader/quantizer вызывается,
исходный код сторонних кернелов не копируется.
