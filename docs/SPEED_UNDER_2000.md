# Кандидат: менее 65 с при пике не выше 2000 MiB

## Вторая итерация: 192 MiB активаций и повторное использование gate/up

Пользователь сообщил первый повтор кандидата `eacf459`: base 76.69 с,
solution 71.62 с, 1713 MiB. Промежуточный s = 1.07079; полного ZIP и
окончательного checks.json этого запуска ещё нет. Это не подтверждение допуска.
При условном best s = 1.5 формула даёт около 5.90 балла за скорость;
при той же базе 65 с соответствовали бы s = 1.17985 и около 14.28 балла.
Это расчёт для заданного best s, а не известный результат других команд.

Новый кандидат:

- Бюджет сохраняемых активаций 64 → 192 MiB: меньше копий CPU–GPU.
- В MLP backward на T4 при количестве строк >512 одна FP16-матрица gate/up
  используется для recompute и dx. Раньше bnb forward распаковывал её внутри,
  после чего dx распаковывал её ещё раз. Для меньших входов и других GPU
  сохранён прежний путь, включая native small-M GEMM.

Выбор границы сверён с локальными wheel-исходниками bitsandbytes 0.50.2:
`backends/cuda/ops.py`, `_gemm_4bit_use_custom_cuda` и fallback. На sm75
для M>512 используется dequantize + F.linear. Вызовы F.linear/matmul и их
формы сохраняются; сторонний CUDA-код не копируется. Один временный gate/up
операнд занимает 52.5 MiB для целевой модели, между слоями не сохраняется.

Оценка запаса относительно первого повтора: 1713 + 128 + 52.5 ≈1893.5 MiB.
Это верхнеуровневый бюджет тензоров, не гарантия внешнего пика: время жизни
тензоров, аллокатор и компиляция могут изменить результат. Новый GPU-замер
обязателен; время <65 с и память ≤2000 MiB пока не подтверждены.

Добавлена реальная форма MLP с 768 строками в тест точных outputs/scaled
gradients, проверяется путь однократной распаковки в backward. GPU-тест
локально не выполнялся из-за отсутствия PyTorch/CUDA. Ниже — описание первой
итерации; её бюджет 64 MiB заменён текущими 192 MiB.

## Первая итерация

Статус: реализован в личной ветке `speed-under-2000`, результат T4 ещё не
получен. Проверенный main остаётся на `4dbd416`: 81.07 с, 817 MiB,
все 10 проверок PASS. Публикация в репозиторий хакатона приостановлена.

## Основание

Версия 817 MiB переносит frozen MLP NF4-веса с CPU для forward и backward
каждого шага (примерно 1.1 GiB/шаг), а streamed head передаёт блоки словаря
для обоих проходов (примерно 890 MiB/шаг). Это экономит память, но добавляет
трафик и вызовы. В проверенном результате training loop занял 56.44 с,
полный запуск 81.07 с. Чтобы достичь 65 с, нужно убрать более 16 с полного
времени; новая политика — гипотеза, а не подтверждённое ускорение.

Предыдущие варианты давали 60–63 с при 5–6 GiB, что не удовлетворяет новому
лимиту 2000 MiB. Старый вариант 74.01 с / 2063 MiB тоже не подходит. Замеры
в разных сессиях не являются изолированным сравнением отдельных оптимизаций.

## Изменения

1. `OFFLOAD_MLP=False` в собственном storage-коде: frozen MLP NF4 остаётся
   на CUDA после штатной загрузки. Убираются CPU-переносы MLP по каждому шагу;
   раннее CPU-размещение большого FP32 embedding/head сохраняется.
2. Полный FP16-операнд head (445.125 MiB) создаётся один раз по реальному
   frozen CPU-весу и повторно используется на CUDA. Вместо прохода по блокам
   словаря используется существующий `_ChunkedHeadLoss`: logits ограничены
   блоками по 256 токенов, все классы и выходы Soup сохраняются.
   Кэш содержит только операнд, не logits/градиенты; обновляется при смене
   версии, указателя, формы/stride исходного веса или устройства исполнения.
   Создание кэша входит в штатное измерение; готовых файлов кэша нет.
3. Повторное сохранение одного и того же неизменённого Tensor в одном
   forward использует одну CPU-копию. Слабая ссылка не удерживает GPU-тензор;
   изменение `_version` требует нового снимка. Другие view/объекты намеренно
   не объединяются. Backward и значения сохранённых тензоров не меняются.

Бюджет GPU saved-активаций остаётся 64 MiB. NF4 всех decoder-матриц занимает
около 624.75 MiB; вместе с FP16 head получается 1069.875 MiB до scales,
активаций, LoRA, временных тензоров, аллокатора и CUDA runtime. Это оставляет
часть бюджета до 2000 MiB, но не доказывает соблюдение внешнего пика:
загрузка, компиляция и фрагментация также входят в исходный замер.

## Проверка

Добавлены GPU-проверки повторного использования head на нескольких шагах,
инвалидации после изменения веса, совпадения выходов и масштабированного
градиента с прежним head. Для saved-tensor hooks проверяются неизменяемые
снимки до/после записи, освобождение исходного Tensor и точный backward.
Интеграционный тест реального локального NF4 checkpoint теперь проверяет
обе политики размещения MLP, не обходя ни загрузчик, ни PEFT, ни LoRA.

Локально GPU/PyTorch отсутствуют; выполнены синтаксический и статический
аудиты. GPU-тесты и полный допуск нового кандидата ещё не подтверждены.
В Kaggle нужны исходные тесты и check_rules.py, два повтора base/solution.
Кандидат принимается только при всех 10 PASS, времени <65 с и внешнем пике
≤2000 MiB; пока эти цели не заявляются достигнутыми.

Модель, данные, батчи, шаги, LoRA/dropout, оптимизатор, флаги Soup, аллокатор
и скрипты `harness/`, `tests/`, `task/`, `templates/` не изменены.
Ни текущие 817 MiB, ни прежние 60–63 с не приписываются новому коду.
