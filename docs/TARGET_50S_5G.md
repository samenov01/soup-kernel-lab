# Цель: до 50 секунд и менее 5000 MiB на T4

Новая цель пользователя: полное время штатного harness ≤50 с и пик GPU
строго <5000 MiB при прежнем качестве, модели, данных и параметрах задачи.
Контроль — `160150ef7560289f520710ce5982918e0cb1d5fb`: 63.25 с,
5959 MiB, eval loss 2.04951. Новая ветка — `speed50-memory5g`.

## Первый кандидат

`c3f0f00c84d1bc02c5281c5fb030230361f05595`, Kaggle 18, один повтор.

- Исходные frozen NF4 параметры используют views тех же неизменённых байтов
  в объединённом packed-буфере. Сами значения, параметры и исходные quantization
  metadata сохраняются; отдельные старые копии packed-весов больше не нужны.
- Chunked head хранит FP16 logits. Существующие CE/entropy кернелы переводят
  значения в FP32 при загрузке: убрана промежуточная полная FP32-копия, а не
  точность вычисления softmax. Argmax исходных Half-значений тот же.
- Native PyTorch memory-efficient attention обрабатывает исходные строки
  батча одним variable-length вызовом. Cumulative offsets отделяют строки:
  attention между примерами по-прежнему невозможен. Повторённые K/V головы
  восстанавливаются в backward; сохраняются только малые исходные K/V.
- NF4 backward распаковывает непосредственно в потребляемый FP16 операнд;
  метаданные исходных весов не изменяются, полного распакованного кэша нет.

Контракт внутренних native attention операций сверён с исходниками
[PyTorch 2.11 native_functions.yaml](https://github.com/pytorch/pytorch/blob/v2.11.0/aten/src/ATen/native/native_functions.yaml).
Это внутренний API с привязкой к проверенной версии PyTorch. Измерения и
допуск ещё должны быть получены; эти изменения сами по себе не доказывают
достижение цели.

### Измерение Kaggle 18

102 unit-теста, 79 регрессионных тестов, **10/10 допуска**.
Base 94.65 с / 14345 MiB / eval 2.04964; solution **62.12 с / 5223 MiB /
eval 2.04954**, speedup 1.5237x, memory ratio 2.7465x. Минимальная
собственная доля 11.9%, разница первой loss 0.01%, всей кривой 0.04%.
Один повтор: результат предварительный. Обе новые цели ещё не достигнуты.
Пик ниже прежнего на 736 MiB; причинное сравнение времени разных сессий
не заявляется. [Исходные измерения](measurements/varlen_shared_v14/).

## Следующий кандидат: пересчёт frozen MLP

Вместо двух широких gate/up-активаций autograd сохраняет узкий вход MLP.
В backward детерминированный frozen gate/up matmul выполняется повторно;
dropout, RNG и trainer gradient_checkpointing не меняются. Используются
исходные SwiGLU кернелы организаторов; их время не считается собственным.
Отдельный GPU-тест сравнивает forward, масштабированный backward и фактически
сохранённые тензоры с прежним merged MLP. Возможна плата временем за снижение
памяти; нужен полный измеряемый запуск, а не расчётный прогноз.

Дополнительно candidate собирает Q/K/V напрямую из BHLD strides, включая
переход в FP16, собственным gather-кернелом. Scatter использует ранее
проверенный кернел projection_io. Это убирает полные transpose/contiguous
копии и последовательности zero-fill/index-copy без изменения значений.
Малые nested scales frozen NF4 декодируются один раз и переиспользуются,
с проверкой версий исходных scale-тензоров. Кэш содержит FP32 масштабы,
а не распакованные матрицы весов; его память входит в измерение пика.

Полный код следующего кандидата:
`33641b98b154e95cb14849c6f3264aee23eefd78`, Kaggle 19, один повтор.

Следующий вариант `a627f3906d01a7f87ba0b465f7565a1b30a2aa4b` объединяет
QKV gather/scatter в custom autograd и делает такие же компактные IO внутри
MLP. Независимый запуск T4 `soup-kernel-layout-probe/1` подтвердил
**119 unit-тестов**, включая FP16/FP32 QKV, padded MLP и сохранение тензоров.
[Диагностика и лог](measurements/layout_probe_v1/).
Это diagnostic-only, а не полное обучение или admission.

Проверены обычный, транспонированный и column-major output GEMM, cuBLAS и
cuBLASLt. На крупных MLP-матрицах устойчивого выигрыша нет: например,
M=1024/K=17920/N=1536 даёт 2.72 мс обычным NN против 2.98 мс TN.
Глобальное переключение BLAS не применено. Отдельные маленькие attention
матрицы выигрывают, но этого недостаточно для заявления цели по wall-time.
Свежий полный кандидат отправлен на два повтора в
`diassamenov/soup-kernel-layout-probe/2`; окончательного результата ещё нет.

### Подтверждение памяти: Kaggle 19

Код `33641b9`: **64.73 с / 3989 MiB / eval 2.04952**.
Base 85.84 с / 14345 MiB / eval 2.04970. Speedup 1.3261x,
memory ratio 3.5961x, eval delta -0.009%. 111 unit-тестов,
79 регрессионных тестов, 10/10 допуска, собственная доля 14.8%.
Это один повтор. [Все исходные файлы](measurements/recomputed_mlp_v15/).
Цель памяти выполнена с запасом, цель времени не достигнута.

Код `c5a1fa1` (Kaggle 20) сохраняет gate/up на нечётных слоях, пересчитывает
на чётных, а также объединяет residual addition и post-attention RMSNorm.
Округление residual и norm backward явно остаётся Half перед последующими
операциями; тест сравнивает с прежними кернелами побитово. Модельные параметры,
dropout, optimizer и флаги не меняются.

Следующий кандидат убирает повторный обход установленных пакетов при импорте
TRL: transformers уже создал полный packages_distributions mapping, который
передаётся без фильтрации. importlib восстанавливается сразу после импорта.
Ни одна библиотека не скрывается от проверок; в диагностике самостоятельный
обход TRL занимал около 2.5 с. Фактический wall-time ещё должен быть измерен.

Следующий эксперимент объединяет autograd LoRA A/B: small gather,
два штатных FP16 GEMM, исходный scaling/add, а в backward — FP16 градиенты
матриц с переводом в исходный dtype trainable параметров и собственный
scatter градиента входа. Native PEFT dropout остаётся за пределами custom
Function: форма, dtype и RNG порядок не меняются. Unit-тест сравнивает
выход и масштабированные градиенты побитово, интеграционный — настоящие
PEFT-проекции, loss и RNG state. Нужна GPU-проверка и полное обучение.

## Сохранённый результат и остановка валидации

Выбран проверенный код `33641b9`, пик **3989 MiB**, время **64.73 с**,
111/79 тестов и 10/10 допуска. [Полный отчёт](T4_RUN_08.md).
Текущая ветка `speed50-memory5g` содержит точно его `solution/`, notebook
закреплён на измеренном SHA. Следующий код `761c03b` сохранён в отдельной
ветке `speed50-next`; он пока не допущен, реальные время/память неизвестны.

Короткий полный запуск нового кандидата с timeout 600 и без дополнительного
профиля отклонён Kaggle: `Maximum batch GPU session count of 2 reached`.
Это отказ Kaggle, не sandbox/approval. Пользователь сообщил, что сеансы
в интерфейсе остановлены, но API продолжал показывать два queued batch run.
Остаток GPU-квоты около 18 минут; отмена через SDK требует session_id,
который публичный API статуса не возвращает. Notebook не удалялись;
исходный пользовательский notebook и репозиторий команды не менялись.
Повторную проверку двух ожидающих версий и квоты нужно сделать перед
следующим submit, чтобы не расходовать квоту повторными экспериментами.

### Два повтора compact IO завершены

`layout-probe/2` позже перешёл из QUEUED в RUNNING и завершился:
**71.23 с / 3731 MiB / eval 2.04955**, 119/79 тестов, 10/10 допуска,
минимальная доля 15.2%. [Подробный отчёт](T4_RUN_09.md).
Память ещё меньше, измеренное время хуже — для цели скорости не выбран.
Контроль `33641b9` остаётся текущим. API показал timeUsed 21653.76 с
при totalTimeAllowed 21600 с: квота исчерпана; новых заданий не отправляли.
Уже поставленный `lab-auto/20` затем перешёл в RUNNING и завершился.

### Смешанное хранение завершено

Kaggle 20, код `c5a1fa1`: **67.47 с / 4451 MiB / eval 2.04953**,
121 unit-тест, 79 регрессионных, 10/10 допуска, доля 15.5%.
[Полный отчёт](T4_RUN_10.md). По абсолютному времени в этой сессии
он не улучшил выбранные 64.73 с; нормированный speedup выше, но прямого
A/B-сравнения алгоритмов нет. Выбран `33641b9`, notebook закреплён на нём.
Все отправленные задания завершены, архивы сохранены. Следующий `761c03b`
остаётся отдельным неподтверждённым экспериментом до появления GPU-квоты.
Итог завершённых измерений: память <5000 MiB достигнута, время ≤50 с не достигнуто.

### Уточнение доступности GPU

После завершения обоих batch-сеансов повторный submit короткого кандидата
`761c03b` принят сервером как `lab-auto/21` (timeout 600, без дополнительного
профиля). Счётчик timeUsed выше totalTimeAllowed сам по себе не был
доказательством отказа в новой сессии; прежний фактический отказ был по двум
одновременным batch-сеансам. Новая валидация ожидается. Проверенное решение
не заменяется до завершения настоящих unit-тестов и полного harness.
