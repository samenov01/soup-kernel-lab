# Исследование цели 2.5x по скорости

Цель пользователя: speedup ≥2.5 по **полному wall-time** штатного harness,
с тем же качеством. Дополнительное ограничение: memory ratio ≥2,
то есть на публичной базе 14345 MiB — пик решения не выше примерно 7170 MiB.
Параметры задачи и файлы организаторов не изменяются.

Контроль: `65da9fc4e5e0cd70bbd81cdabe329df02c496853`, метка
`t4-validated-memory-v5`. Его два повтора дали speedup 1.3391x и memory ratio
2.3574x; [результат](T4_RUN_04.md). Новые опыты находятся в `speed-25x`.

## Проекции attention и RoPE: версия Kaggle 10

Код `9465510344ee1a684662f57403515b54477b14a3`.
Pointwise-проекции attention считают только действительные позиции;
LoRA dropout вызывается с прежними формами и сохраняет состояние RNG.
Собственный RoPE объединяет отдельные rotate/multiply/add и их backward.

Одна полная пара: base 86.13 с / 14345 MiB, solution 74.54 с / 6497 MiB.
Speedup **1.1555x**, memory ratio **2.2079x**, eval loss 2.04968 → 2.04963.
88 unit-тестов, 79 регрессионных тестов и все 10 проверок допуска прошли.
[Исходные файлы](measurements/projections_rope_v7/).

### Найденный изъян

RoPE специализировал длину батча и strides как constexpr. Для разных длин
короткого 64-шагового обучения это вызывало множество компиляций.
В measured run события вокруг RoPE суммарно дали 12.35 с, при этом GPU-профиль
готовых операций не показывает сопоставимого времени самого кернела.
CUDA events вокруг CPU-компиляции захватывают и ожидание; reported own share
34.3% нельзя интерпретировать как чистую долю GPU-работы RoPE.

В следующем кандидате длина и strides передаются runtime-параметрами;
grid отдельно задаёт batch/head. Специального прогрева по данным вне замера
или подготовленных кэшей нет: обычная первая компиляция входит в wall-time.

## Следующий кандидат: версия Kaggle 11

Код `ec3f2ca829977e386747b8283f03b1cd2680f95e`.
Кандидат отклонён по измерению скорости.

- Runtime-длины в RoPE и attention вместо специализации каждой длины батча.
- Собственный masked causal GQA без материализации полной матрицы attention
  и без повторения K/V для каждой query-head. Вероятности восстанавливаются
  блоками в backward, K/V-градиенты округляются по головам в FP16 и затем
  суммируются в FP32, как в исходной repeat → cast → SDPA цепочке.
- Gate/up frozen MLP объединяются в одно умножение. Во время измеряемого
  запуска создаются дополнительные **упакованные NF4** веса и metadata;
  полного FP16/FP32 weight-cache нет. Реальные параметры и экспорт адаптера
  не меняются. Фактический пик и изменение округления градиентов должны
  пройти GPU-тесты и полное сравнение качества.

Тесты attention сравнивают выход и градиенты при AMP scale=1 и 65536,
включая left/right padding и длину 512. Gate/up отдельно проверяется на
реальной ширине 1536/8960. Допуск по памяти оценивается по итоговому пику,
а не по расчётному размеру дополнительных буферов.

Источник математической идеи online softmax: оригинальные статьи
FlashAttention, ссылки в [документации Triton](https://triton-lang.org/main/getting-started/tutorials/06-fused-attention.html).
Код attention написан самостоятельно, сторонние реализации не переносятся
и готовые kernel-библиотеки не используются. Native SDPA остаётся fallback
для неподдерживаемых режимов. Реализация новых кернелов сама по себе ещё
не доказывает ускорения на T4.

### Фактический результат версии 11

96 unit-тестов и 79 регрессионных тестов прошли. Шаги, outputs и loss-кривая
совпали в допусках, eval loss 2.04961 → 2.04962 (+0.000% в summary).
Память 14345 → 6755 MiB, ratio 2.1236x, соответствует ограничению пользователя.
Полное время **87.68 → 108.28 с**, speedup **0.8098x**; штатная проверка №8
не пройдена. Всего 9/10 допуска, кандидат непригоден.
[Все исходные данные](measurements/gqa_merged_rejected_v8/).

В 16 профильных шагах собственный dQ занимает 4072.60 мс, dK/dV — 2665.74 мс,
forward — 475.13 мс. Для сравнения: native backward в предыдущем профиле
занимал 538.09 мс. Это прямое основание убрать собственный GQA; его
компиляционная корректность и сохранение loss не означают быстродействия.
Алгоритм полностью сохранён в коммите `ec3f2ca`; из текущего solution удалён.
RoPE после runtime-исправления занимает 80.71 мс за 1792 вызова в профиле.

## Следующие отдельные измерения

Версия 12: `37337b11a61b56cbd5544bec2b429e2f46894bf3`, два повтора.
Native SDPA, runtime RoPE, merged gate/up и собственные gather/scatter,
которые объединяют cast и заполнение padding нулями. Отдельный тест требует
побитового совпадения этого перемещения и масштабированного градиента.

Результат: 93 unit-теста, 79 регрессионных тестов, 10/10 допуска.
Полное время 83.31 → 67.12 с (**1.2412x**), память 14345 → 6363 MiB
(**2.2544x**), eval loss 2.04967 → 2.04965 (-0.001%).
Solution-повторы 67.14 и 67.10 с; память 6363 MiB в обоих.
Все ограничения соблюдены, но прежний результат не улучшен.
[Исходные данные](measurements/native_merged_io_v9/).

За 16 профильных шагов GPU-kernel time составил 6.281 с против 8.255 с
контрольного профиля в другой сессии. Это не эквивалентное ускорение всего
обучения: полное время включает CPU, запуск и компиляцию. Внутри LoRA найден
лишний full scatter → gather между A и B, который следующий кандидат убирает.

Версия 13: `a7d8cf2bc3825de088595182c14e6efa8a5c045b`, два повтора.
Frozen base Q/K/V объединяются в один packed-NF4 matmul. Штатный PEFT forward
продолжает считать LoRA, scaling и dropout; вход и формы dropout не меняются.
Контекст проверяет, что все три предварительно посчитанных base-выхода
реально потреблены, иначе запуск завершается ошибкой. Новые буферы содержат
packed NF4 и масштабы, а не распакованные веса. Пик VRAM должен пройти
реальный замер; расчёт сам по себе не подтверждает соблюдение 7170 MiB.

Подготовленный следующий код `7d04597107fe8a699d2f2883e556267ed46a6273`
убирает full scatter/gather между LoRA A и B. Native dropout вызывается с
исходной формой, dtype и RNG-порядком; обе матрицы считаются последовательно
на действительных строках. Два собственных кернела объединяют scatter,
scaling и сложение с fp32 base, а также обратный gather/scale. Они явно
сохраняют fp16-округление до/после scaling. Поддерживаются точные степени
двойки scaling (в задаче 2.0); другие варианты сохраняют исходный PEFT путь.
Отдельные тесты требуют побитового совпадения значений и AMP-градиентов,
а интеграционные сравнивают LoRA gradients и состояние RNG.

## FP16-хранение активаций: версия 15

Код `1357b0d467c3fd28a9bd6e37ae8758ce9d314990`, два повтора, результат ожидается.
Внутри ordinary fp16 SFT decoder используются Half-активации и residual storage.
Веса модели, dtype trainable-параметров, optimizer, данные, шаги и флаги trainer
не меняются. RMS-статистики и производные нормализации вычисляются в FP32;
финальная нормализация возвращает FP32 для прежнего chunked head.
Обычные внешние model/eval-вызовы сохраняют предыдущий путь.

Этот вариант **не побитово тождественен** FP32-активациям: меняется округление
в residual/промежуточных значениях. Native dropout сохраняет p, порядок вызовов
и формы; переход dtype не сопровождается обещанием прежних битовых масок RNG.
Поэтому нужны настоящие per-step метрики, кривая и adapter eval, а не только
unit-тест формы/dtype. Отдельный тест проверяет фактический Half-вход decoder,
FP32 final norm, сохранность dtype всех параметров и отклонение градиентов.
Для sparse LoRA добавлено побитовое сравнение Half-base scaling/gradient.
Режим включается по контракту FP16 training caller; проверки, profiler и
измеряемое обучение не распознаются и не получают разных реализаций.
