# Цель: пик GPU строго менее 2250 MiB

**Достигнута:** код `3088ce8cca7b54ddaa101afbf3196b02d9b9ff0a`,
2063 MiB в каждом из двух полных повторов, 74.01 с по медиане,
eval loss 2.04949. Все 10 проверок допуска пройдены.
[Отчёт, точные SHA256 и исходные файлы](T4_MEMORY_2250.md).
В проверенном варианте используется полный Half head на GPU и бюджет
saved-активаций 256 MiB. Streamed head ниже описан как ранний эксперимент;
в этом результате он не используется. Далее сохранена история разработки.

Новая ветка `memory2250`, основа — проверенный `a627f39`: 3731 MiB,
71.23 с в двух повторах. Все параметры задачи, данные, порядок батчей,
LoRA, optimizer, scheduler и флаги Soup сохраняются. Командный репозиторий
не меняется; разработка идёт в отдельной личной ветке.

## Первый экспериментальный кандидат

- Frozen tied embedding/LM-head вес переносится на CPU перед стандартной
  подготовкой PEFT, чтобы не создавать одновременно полные Half/Float CUDA
  копии. Объект Parameter, его значения, FP32 dtype после PEFT и связь
  embedding/head остаются прежними. Обучаемые LoRA-параметры остаются на CUDA.
- Embedding выбирает исходные FP32 строки на CPU и возвращает их на исходную
  CUDA GPU; штатный hook входного градиента остаётся на месте.
- Head проходит весь словарь блоками 8192. На CPU хранится pinned Half-копия
  исходных frozen весов, на GPU находится только текущий блок. Собственные
  кернелы объединяют устойчивые CE/entropy статистики и argmax. В backward
  учитывается настоящий GradScaler scale; частичные Half GEMM накапливаются
  в FP32, полный входной градиент один раз округляется в Half.
- Крупные сохранённые decoder-активации перемещаются в pinned CPU memory
  через собственные pack/unpack hooks. Копии lossless; исходный dtype и
  CUDA device восстанавливаются в backward. NF4 packed параметры и малые
  тензоры не выгружаются.

Встроенные `activation_offloading`, `gradient_checkpointing`, `packing`,
`padding_free`, `use_cut_ce` не включаются. Это собственный код хранения
тензоров и streamed head. Передача CPU/GPU и создание CPU-копий входят в
обычный замер; фоновых процессов, другой GPU и внешних кэшей нет.

Разбиение GEMM по словарю меняет порядок редукции. Нельзя заявлять
побитовую идентичность dense backward; тестируются loss, entropy, accuracy,
масштабированные градиенты, а затем полная кривая и adapter eval.
На этом этапе цель ещё не была подтверждена измерением. Возможное замедление
должно было пройти исходный допуск времени ≤110% базы.

Первый код `6c0f1a2` отправлен в приватный `soup-kernel-memory2250/1`:
одна полная пара base/solution без дополнительного профилирования.
Следующий вариант оставляет до 512 MiB реально нужных saved-активаций на GPU,
остальное выгружает на CPU. Это верхний бюджет, без резервирования или
выделения неиспользуемой памяти; алиасы одного storage считаются один раз.
Отдельный тест проверяет точный round-trip и размещение при переполнении бюджета.

## Первая ошибка интеграции

Первый запуск прошёл 127 GPU unit-тестов и 79 регрессионных, но обучение
остановилось до первого шага: после PEFT framework placement снова перенёс
embedding на CUDA. Наш runtime guard отказал, admission не пройден.
Наблюдавшиеся до ошибки 1701 MiB не считаются результатом цели.
[Полный лог и исходные проверки](measurements/host_placement_failure/).

Исправление восстанавливает CPU storage после обычного model.to через
Qwen2ForCausalLM._apply, сохраняя запрошенную CUDA GPU для остальных слоёв.
Новый тест выполняет реальное model.to(cuda) после offload и проверяет
точные значения, tie embedding/head и dtype.

Следующий вариант оставляет полный Half head-операнд на GPU во время
forward/backward, сохраняя исходные GEMM shapes и FP32 параметр на CPU.
Это альтернативный баланс с меньшим числом пересылок. Его пик ещё не измерен;
streamed vocabulary реализация сохранена и отдельно тестируется. Прямой
unit-тест требует побитового совпадения с предыдущим chunked head.

## Проверка варианта с бюджетом активаций

`soup-kernel-memory2250-fast/1`, исходники `ae3d361ba88d47ea4676f566f7ba9d936a8bd2ab`:
128 GPU unit-тестов и 79 регрессионных прошли. Этот вариант ещё не содержит
исправления framework placement и также остановился до первого шага на
`Frozen embedding unexpectedly moved from host storage`.
**7 из 10 проверок допуска не пройдены**: завершение, работа собственных
кернелов, их доля времени, сохранение задачи/выходов, loss-кривая, eval и
время/память. Прошли только запрет готовых библиотек, чистота измерения и
регрессионные тесты. Неполный запуск не подтверждает цель по памяти.
[Исходный result, checks и логи](measurements/host_budget_placement_failure/).

Исправленный вариант с полным Half head и восстановлением CPU storage
после `_apply` — `51775b5a8d94acf96fe6e1bb480d3dcb711d1ef8`,
`soup-kernel-memory2250/2`; этот notebook позднее удалён пользователем.

Параллельный исправленный кандидат оставляет до 256 MiB saved-активаций
на GPU вместо 512 MiB; полный Half head и исправление `_apply` те же.
Это сравнение двух политик хранения с неизменной математикой обучения;
дополнительные CPU-пересылки могут увеличить время. Оба варианта требуют
полного admission; более низкий бюджет сам по себе результата не гарантирует.

После просьбы ограничиться одним тестом пользователь удалил оба ожидавших
экспериментальных notebook. Для одного выбранного кандидата с бюджетом
256 MiB подготовлен `3088ce8`; пользователь затем самостоятельно выполнил
Run All в своём Kaggle и прислал `kernel_results (1).zip`. В архиве две полные
пары base/solution и дополнительный профиль. Новые GPU-прогоны после получения
этого результата для его подтверждения не требовались.
