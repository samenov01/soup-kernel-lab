# Цель следующей серии: speedup >=2 и memory ratio >=2

Точка отсчёта — неизменённый Soup из стартового harness. Проверенная версия
RMSNorm сохранена меткой `t4-validated-rmsnorm-v3`, код `4ae12d7`.
Её публичный T4-результат: speedup 1.0814x, memory ratio 1.1584x,
68 unit-тестов, 79 регрессионных тестов и все 10 проверок.

Текущая ветка `memory-speed-2x` содержит новые эксперименты. Цель 2x ещё
не достигнута; результаты сохранённых версий не относятся к новым изменениям.
Задача, данные, число шагов и настройки обучения сохраняются.

## Первый эксперимент: компактные gate/up MLP

В bitsandbytes 0.50.2 `Linear4bit.forward` приводит вход к compute_dtype,
делает матричное умножение, затем приводит результат обратно к dtype входа.
При frozen fp16 MLP и fp32 входе это оставляет gate/up в fp32, хотя все их
значения уже округлены до fp16. SwiGLU-пример сохраняет эти большие тензоры
для backward на всех 28 слоях.

`solution/compact_mlp.py` передаёт отдельные fp16-копии входа в gate и up,
сохраняет их исходные fp16-результаты и выполняет SwiGLU в fp32 прежними
кернелами примера. Результат SwiGLU и выход всего MLP остаются fp32.
Backward вычисляется в fp32, но каждое ответвление приводит градиент
к fp16 в той же точке, где это делал прежний обратный проход Linear4bit.
Отдельные преобразования входа важны: общая копия заставила бы складывать
градиенты gate/up в fp16 и изменила бы округление.

Путь включён только для CUDA fp32, silu, трёх точных frozen Linear4bit
без bias с заранее установленным compute_dtype=fp16 и готовым quant_state.
LoRA-проекции и неподдерживаемые конфигурации используют прежний путь.
Матричные умножения, квантованные веса и параметры остаются прежними.

Это не новый собственный SwiGLU: исходные example_* кернелы не изменены,
не переименованы и по-прежнему не учитываются в доле собственных кернелов.

Три новых GPU-теста сравнивают output и input-gradient побитово, проверяют
вдвое меньший размер сохранённых gate/up через saved_tensors_hooks,
включают форму Qwen (4,512,1536)->8960 и fallback на обычном MLP.
На полном обучении точный выигрыш по памяти/времени пока не измерен.

В автоматизации добавлен выбор 1 или 2 повторений штатного harness.
Для промежуточных итераций допустим один парный запуск; окончательный
кандидат проверяется с двумя повторами. Каждый train-run остаётся 64-шаговым.

### Результат первого опыта

Kaggle auto, версия 2; коммит `8611deadd3ae68bb84353d2ed23e99337b123077`.
71 тест solution, 79 регрессионных тестов и 10 проверок прошли.
Один парный запуск: base 78.59 с / 14345 MiB / loss 2.04969;
solution 74.53 с / 10343 MiB / loss 2.04966.
Speedup 1.0545x, memory ratio 1.3869x. Это промежуточное сравнение с одним
повтором; оба целевых коэффициента 2x пока не достигнуты.

## Второй эксперимент: блочный LM-head и метрики

`solution/chunked_head.py` реализует ограниченное хранение logits: блоки
по 256 токенов вместо полного B*T*V. В одном проходе вычисляются настоящие
CE, entropy и argmax; они агрегируются с теми же labels/attention_mask,
числом токенов и нормализацией num_items_in_batch. Soup получает реальные
per-token losses через свой протокол rewind для шагов без плотного logits.
Встроенные режимы Soup не включаются, TrainerArgs не изменяются.

Backward пересчитывает блоки logits и применяет текущий upstream gradient
(включая GradScaler) до преобразования dlogits в fp16. Так сохраняется место
AMP-округления относительно исходного dense backward. Frozen lm_head weight
не меняется; его fp16-копия соответствует обычному autocast и сохраняется
только как операнд текущего backward.

Оптимизация включена только внутри обычного single-device fp16 SFT loss
на Qwen2 с frozen fp32 head, nll, без label smoothing/DFT/виртуальных токенов,
packing и других несовместимых режимов. За пределами этого пути модель
сохраняет исходный forward и плотные logits. Это рабочий dispatch по
контракту вызывающего trainer, а не распознавание тестов или harness.

Новые тесты проверяют loss, entropy, predictions, градиенты при scale=1
и scale=65536, отсутствие сохранённого плотного logits, реальные SFT-метрики,
совместимость с преобразованием output в fp32 и row-loss протоколом Soup.
Из-за разбиения GEMM возможны обычные различия порядка fp32 накопления;
окончательную корректность решают полные проверки кривой/метрик/адаптера.

Дополнительно SwiGLU output сразу округляется в fp16 в прежней точке
преобразования перед down_proj; наружный выход MLP остаётся fp32.
Те же побитовые MLP-тесты должны подтвердить сохранение его семантики.

### Проверка подключения второго опыта

Версия Kaggle 3 (`dbd0d07`) прошла 78 тестов и 10 проверок, но новый head
в обучении не активировался: число вызовов vocabulary-кернелов осталось прежним,
пик — 10343 MiB. Причина: Accelerate включает autocast внутри model.forward,
а trainer-обёртка проверяла его до вызова модели. Этот запуск не считается
измерением блочного head. Исходные результаты сохранены в
`docs/measurements/chunked_head_inactive/`.

Проверка перенесена: trainer читает реальные неизменённые args.fp16/bf16,
а model.forward валидирует фактический autocast внутри Accelerate.
Интеграционный тест теперь моделирует этот порядок без внешнего autocast
вокруг trainer.compute_loss. Следующий запуск должен подтвердить реальную
смену структуры вызовов и память, а не только успешный статус тестов.

Версия 4 (`0e63d4a`) выявила обращение к отсутствующему в реальном SFTConfig
полю past_index. Оно заменено опциональным getattr; интеграционный тест
теперь использует настоящий SFTConfig вместо заглушки аргументов.

Версия 5 (`90340e9`) в штатном `--only solution` завершила 64 шага:
83.03 с, 6423 MiB, eval loss 2.04964; 78 тестов и 79 регрессионных тестов
прошли, собственная доля 7.6%. Это предварительный memory ratio около 2.23x
относительно прежней базы 14345 MiB, но официального парного сравнения здесь
нет: проверки, требующие base, ожидаемо провалены. Их результат не подменялся.

## Третий эксперимент: необходимые строки и padding

Forward head считает объединение позиций attention_mask и всех позиций
с supervised shifted label. Это сохраняет даже граничную метку при левом
padding. Остальные позиции не нужны ни loss, ни entropy, ни accuracy.
Backward пересчитывает только строки с ненулевым CE-градиентом; полный
градиент восстанавливается на исходных позициях с нулями для ignore_index.
Actual upstream AMP scale по-прежнему применяется до fp16 округления.

Frozen MLP обрабатывает только действительные позиции исходной 2D mask.
Сами input_ids, attention_mask, порядок строк, attention и LoRA Q/V dropout
не сокращаются. Поэтому исходный порядок RNG для dropout сохраняется.
При необычной supervised-метке в left padding MLP-compaction отключается.
Батчи не перемешиваются; встроенные packing/padding_free не включаются.

Проверяются left/right padding, граничная shifted label, полностью
игнорируемые метки и реальные valid-token outputs/градиенты модели.
Окончательный кандидат требует парного сравнения с двумя повторами.

## Независимый matmul probe

`experiments/nf4_gemm_probe.py` — собственный диагностический fused NF4
matmul на tl.dot. Он не импортируется из solution и не подменяет операции
обучения. Проверяется на четырёх формах MLP и трёх tile-конфигурациях против
нынешней NF4-деквантизации + matmul. Результат микробенчмарка сам по себе
не считается speedup обучения и не участвует в доле 5%.

Обе версии probe отклонены по результатам настоящего T4. Вторая версия
(`65da9fc`, Kaggle 7) проверила все 12 комбинаций: численная проверка прошла,
но лучшее время для `[512, 8960, 1536]` — 10.66 мс против 0.91 мс у текущего
пути. Компилятор показал 76–1086 spills: промежуточные значения уходят из
регистров в память. Другие формы также медленнее. Данные сохранены в
`docs/measurements/gemm_probe_v2/`; этот kernel не подключён к решению.

Kaggle 8 проверяет `65da9fc` штатным harness с двумя повторами base/solution.
Это первая полная проверка объединения sparse head и padding MLP; результаты
предыдущего solution-only запуска не заменяют её.

## Дополнительный кандидат: dtype NF4 backward

В исходном `MatMul4Bit.backward` из bitsandbytes 0.50.2 frozen-вес
распаковывается с dtype исходного QuantState (fp32), затем сразу переводится
в dtype градиента (fp16). `solution/nf4_backward.py` передаёт исходному backward
временное shallow-copy представление metadata с dtype fp16. Собственный unpack
по-прежнему умножает codebook на scale в fp32 и округляет при записи; ожидается
тот же fp16-операнд без промежуточной полной fp32-матрицы.

Реальный QuantState, packed-веса и scales не меняются. Представление metadata
существует только во время вызова backward; распакованные веса не кэшируются.
Другие dtype, FP4 и несовместимые случаи используют исходный путь. Четыре
теста требуют побитового совпадения forward и input-gradient, проверяют
фактическую распаковку в fp16 и неизменность исходного dtype. Этот кандидат
ещё не измерен и не входит в запущенную Kaggle-версию 8.
